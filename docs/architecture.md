# PaperPilot Architecture

PaperPilot is an evidence-backed research investigation engine. A user asks a
technical research question; PaperPilot discovers papers, retrieves permitted
open-access text, extracts structured evidence with source passages, compares
experiments with deterministic rules, and produces a traceable report.

This document describes the target architecture. Sections marked **(planned)**
are not implemented yet; see [roadmap.md](roadmap.md) for status.

## 1. Shape of the system

```
            ┌──────────────┐   HTTP/JSON    ┌──────────────────────────┐
 Browser ──▶│  frontend    │──────────────▶│  api (FastAPI)           │
            │ React + Vite │   /api/v1/*    │  modular monolith        │
            └──────────────┘                └───────────┬──────────────┘
                                                        │ one transaction:
                                                        │ state row + outbox row
                                                        ▼
                                             ┌──────────────────────┐
                                             │ PostgreSQL + pgvector │◀─────────┐
                                             │ (source of truth)     │          │
                                             └──────────┬───────────┘          │
                                     outbox dispatcher  │ (planned)            │ persist results,
                                                        ▼                      │ then commit offset
                                             ┌──────────────────────┐          │
                                             │ Kafka (single node)   │──────▶ workers (planned)
                                             └──────────────────────┘   discovery / documents /
                                                                        evidence / validation / report
```

**Modular monolith + a few workers.** All HTTP endpoints live in one FastAPI
application split into modules (investigations, papers, retrieval, evidence,
reports, events). Background work runs in separate worker processes that import
the same Python package but run different entry points. This gives clear
boundaries without the operational cost of many microservices. See
[ADR 0001](adr/0001-modular-monolith-with-workers.md).

**PostgreSQL is the source of truth.** Every investigation, task, paper, chunk,
evidence record, and report lives in Postgres. Kafka carries *notifications that
work is ready*, identified by IDs; it never holds the only copy of anything.

## 3. Investigation state machine

```
queued ──▶ running ──▶ completed
   │          ├──────▶ partially_completed   (some papers/tasks failed permanently)
   │          └──────▶ failed                (nothing usable produced)
   └──────────┴──────▶ cancelled
```

Terminal states: `completed`, `partially_completed`, `failed`, `cancelled`.
The discovery worker moves an investigation to `running`. The report worker
(M6) ends it: `completed` when every paper went through every stage, or
`partially_completed` when a paper failed permanently or had no text. Evidence
strength is reported separately, so a report with insufficient evidence still
belongs to a completed investigation.

Task states (M3): `pending → running → succeeded | failed_retryable →
(retry) | failed_permanent | skipped`.

## 4. Database schema

Implemented in M1 (`backend/migrations/versions/0001_*`):

**investigations**
| column | type | notes |
|---|---|---|
| id | uuid PK | generated by the API |
| question | text | 10–500 chars, CHECK constraint |
| status | text | CHECK in the six states above |
| created_at / updated_at | timestamptz | server defaults |

Index: `ix_investigations_created_at` (recent-investigations list, newest first).

Implemented in M2 (`0002_*`):

**papers** — normalized metadata from a provider. `unique(provider, provider_id)` makes
upserts idempotent. `doi` is indexed but not unique, because providers sometimes hold
duplicate records for one DOI. `metadata_fetched_at` records provenance. Open-access URLs
are stored only if they are http(s).

**paper_search_cache** — one row per distinct search request (sha256 of the normalized
query and filters): ordered paper references with relevance scores, the provider total,
and `fetched_at`. Rows younger than 24 h answer repeated searches without a provider call.
Because each key is refreshed at most once per 24 h, counting rows with
`fetched_at` in the last 24 h equals the number of provider calls, which enforces the
daily provider-call cap.

Implemented in M5 (`0005_*`, `0006_*`): `paper_documents` (one per paper:
full text, abstract, or none, with fetch provenance and extractor version),
`paper_chunks` (page-exact text, generated `tsvector` with a GIN index,
`vector(384)` with an HNSW cosine index, embedding model version),
`evidence_records`, append-only `evidence_validations`, and
`fetch_host_schedule` (shared per-host request spacing).

Planned tables (added by the milestone that first needs them):

| Table | Key columns | Key constraints | Milestone |
|---|---|---|---|
| investigation_papers | investigation_id, paper_id, rank, retrieval_method, score | PK(investigation_id, paper_id) | M3 (discovery worker links papers to investigations) |
| outbox_events | event_id, topic, partition_key, event_type, schema_version, payload, published_at | partial index where published_at is null | M3 |
| processed_events | consumer_group, event_id | PK(consumer_group, event_id) — idempotency | M3 |
| investigation_tasks | investigation_id, kind, subject_id, status, attempts, next_attempt_at, last_error | unique(investigation_id, kind, subject_id) | M3 |
| comparison_results | investigation_id, rules_version, matrix, warnings | | M6 |
| investigation_reports | investigation_id, version, content, generator_version | unique(investigation_id, version) | M6 |

`finding_status` values: `reported`, `not_found`, `uncertain`, `unavailable`,
`not_applicable`. "Not found" never means "false".

## 5. Kafka event contracts

Envelope, serialized as JSON and validated with Pydantic on both sides:

```json
{
  "event_id": "uuid",
  "event_type": "investigation.requested",
  "schema_version": 1,
  "investigation_id": "uuid",
  "entity_id": "uuid",
  "occurred_at": "2026-10-22T12:00:00Z",
  "correlation_id": "uuid",
  "causation_id": "uuid | null",
  "payload": {}
}
```

| Topic | Event type | Partition key | Why that key |
|---|---|---|---|
| Topic (partitions) | Event type | Partition key | Why that key | Status |
|---|---|---|---|---|
| investigation-requests (3) | investigation.requested v1 | investigation_id | one discovery run per investigation, ordered | M3: produced by API, consumed by discovery workers |
| paper-discovered (6) | paper.discovered v1 | paper_id | spreads per-paper work across partitions/workers | M3: produced by discovery; consumer arrives in M5 |
| document-processed | document.processed | paper_id | keeps a paper's stages ordered | planned M5 |
| evidence-extracted | evidence.extracted | paper_id | same | planned M5 |
| evidence-validated | evidence.validated | investigation_id | report stage aggregates per investigation | planned M6 |
| investigation-failures (1) | *.dead_lettered | original key | dead-letter topic for inspection and replay | topic created in M3; used in M4 |

Contracts live in `backend/app/events/envelope.py`. Each `(event_type,
schema_version)` maps to one Pydantic payload model; readers reject unknown
pairs. To change a payload, add `v2` beside `v1`, deploy consumers that read
both, then switch producers. Topics are created by `kafka-init` from
`TOPIC_PARTITIONS`; broker auto-creation is off so a typo cannot create a topic.
Retention is 7 days, which allows replay by resetting a consumer group's offsets.

Rules: payloads carry IDs and small metadata, never PDFs or chunk text.
Consumers commit offsets only after their DB transaction (results + a
`processed_events` row) commits. Delivery is **at-least-once**; idempotent
consumers make duplicates harmless. We do not claim end-to-end exactly-once.
See [ADR 0003](adr/0003-kafka-transactional-outbox.md).

## 6. M3 workflow

```
POST /investigations ──one transaction──▶ investigations + investigation_tasks(pending)
                                          + outbox_events(investigation.requested)
outbox-dispatcher ── claim rows with a 30 s lease (FOR UPDATE SKIP LOCKED), commit
                  ── publish with idempotent producer (acks=all), no transaction open
                  ── mark published, or back off 2^attempts s (max 300 s)
discovery-worker (group discovery-workers)
   1. skip if processed_events has (group, event_id)
   2. claim task: UPDATE ... WHERE status IN (pending, failed_retryable)
      OR running for > 10 min (crashed worker); investigation queued → running
   3. search OpenAlex (cached, capped) with no transaction open
   4. one transaction: investigation_papers + paper.discovered outbox events
      + task succeeded + processed_events row
   5. commit the Kafka offset
```

Investigation status after discovery stays `running`, because the later stages
do not exist yet and the investigation is not finished.

### Failures, retries, and dead letters (M4)

| Situation | Handling |
|---|---|
| Provider unavailable or quota spent | task `failed_retryable`, `next_attempt_at` set; a new `investigation.requested` event goes to the outbox with `available_at` = now + 30 s·2^(n−1) (max 15 min, ±20% jitter); the current message is committed so the partition keeps moving |
| Attempt `DISCOVERY_MAX_ATTEMPTS` (4) fails | task `failed_permanent`, investigation `failed`, message dead-lettered (`retries_exhausted`) |
| No papers found | task `failed_permanent` immediately (retrying will not help) |
| Message not parseable / unknown version | dead-lettered (`unparseable`) without calling the handler |
| Handler raises (bug, database down) | seek back and retry with backoff; after 5 consecutive failures dead-lettered (`handler_error`) |
| Dead-letter publish fails | offset not committed; the message is retried (nothing is dropped silently) |

Dead-letter records (`investigation-failures`, schema `DeadLetterRecord` v1)
hold the exact original bytes plus reason, failure kind, consumer group, and
original topic/partition/offset. `app.ops.dead_letters` lists, shows, and
replays them; see [operations.md](operations.md).

Verified failure behavior (local Compose, 2026-10-23; M4 drills in roadmap.md):

| Drill | Observed |
|---|---|
| Kafka stopped while creating an investigation | outbox row stayed unpublished with attempts and error recorded; after restart it was published and processed (25 papers linked) |
| Discovery worker stopped | event waited in Kafka; on restart the worker processed it (25 papers linked) |
| Two discovery workers | consumer group split the 3 partitions 1/2; both processed events; lag 0 |
| Duplicate and 4 concurrent deliveries (tests) | papers linked and events emitted exactly once |
| Dispatcher crash after publish (tests) | rows republished after the lease expired; consumers de-duplicate |

## 7. Documents, retrieval, and evidence (M5)

```
paper.discovered ─▶ document-worker (group document-workers, ml image)
   permitted?  OpenAlex says open access and lists a PDF ─▶ SafeFetcher
               (SSRF checks, robots.txt, shared crawl-delay schedule)
   PyMuPDF text per page ─▶ ~900-char chunks inside one page ─▶ MiniLM embeddings
   else abstract (reason recorded) ─▶ paper_documents + paper_chunks (shared by investigations)
   ─▶ document.processed (key: paper)
document.processed ─▶ evidence-worker (group evidence-workers, ml image)
   hybrid search (FTS + vector, RRF) for the question and one query per field
   rules-v2 extraction: exact sentence, page, chunk, retrieval method
   checks-v1 validation: quote in stored text, page consistent, numbers in quote, value range
   ─▶ evidence_records + evidence_validations ─▶ evidence.extracted (key: investigation)
```

Field outcomes: `reported` (quoted), `uncertain` (quoted, unit unclear),
`not_found` (full text searched, nothing matched), and `unavailable` (abstract
only). Absence is never recorded as a negative finding. Details and
trade-offs: [ADR 0006](adr/0006-documents-retrieval-and-evidence.md);
measured quality: [evaluation.md](evaluation.md).

## 8. Comparison and reports (M6)

```
evidence.extracted ─▶ report-worker (group report-workers, api image)
   wait until every per-paper task is terminal; claim the build_report task (once)
   load verified evidence + absence records; merge duplicate works (same title)
   compare-v3: per-paper matrix; groups only when metric, dataset, protocol, unit known
               claims "A outperforms B" from one clause; opposite claims = conflicts
   report-v1: 3–5 findings from templates, strength by published counting rules,
              question-aware bottom line, limitations / missing information / open questions
   ─▶ investigation_reports (new immutable version) ─▶ investigation completed | partially_completed
```

The UI reads `GET /investigations/{id}/report` (level 1 summary, level 2 findings
expanding in place) and `GET /evidence/{id}` (level 3 inspector: quotation, page,
source document, retrieval and extraction provenance, validation checks). Design and
trade-offs: [ADR 0007](adr/0007-comparison-and-reports.md).

## 9. Delivery guarantees in one paragraph

The API writes the investigation row and its outbox event in one Postgres
transaction, so either both exist or neither does. The dispatcher may publish an
event more than once (crash after publish, before marking it sent). Consumers
may see an event more than once (crash after processing, before committing the
offset). Both are safe because each consumer records the `event_id` it handled
in the same transaction as its results and skips IDs it has already seen.
